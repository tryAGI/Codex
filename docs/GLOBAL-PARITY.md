Acceptance baseline: rust-v0.172.0, commit 3d86e43b075adeba2193ec5c22ac92f55afd82e6. This is not the packaged protocol baseline.

## Inventory and evidence

Run `python3 -B scripts/global-parity.py refresh` once to generate a verified tree/manifest/schema inventory from the pinned public archive. It checks Git blob hashes against the non-truncated upstream tree. Run `check`, `self-test`, `report` or `gate` offline. The catalog parser is shared with the packaged protocol generator. The source list, lexical API and Rust test candidates are navigation evidence, not semantic coverage or a final denominator. Crate, feature, platform target, configuration and RPC rows are provisional until independently reviewed. State transitions and dynamic/generated APIs need explicit reviewed scenarios. Every applicable capability needs exact implementation, test and evidence references.

Four separate lanes: native SDK (no Rust process), host adapters (real effects/permissions/platforms), optional Rust App Server interoperability, and real provider acceptance. A raw method catalog, generic JSON-RPC, skipped test or a successful mock does not prove native behavior. Unknown is not N/A. No percentages until the respective denominator is reviewed; N/A must have an independently accepted rationale. No accepted rows are manufactured by this initial generator.

Realtime delegates to #25 and its existing matrix/evidence runner. The global inventory records source files and links realtime candidates without copying their statuses or evidence. Unresolved or ambiguous references require review by the #25 owner. Do not close #25 on behalf of Agent 5.

## Independent review overlay

`docs/global-parity-reviews.json` records per-capability, per-lane decisions without rewriting the upstream inventory. Each decision binds a full published commit, exact source references, owner and rationale. Source review, missing behavior, divergence, justified N/A and receipt-backed passes are separate. Changed source references invalidate source review; changes to the source tree invalidate negative conclusions and accepted receipts. Typed-only App Server review never receives native credit. A lane without a verified platform, Rust-runtime or live-provider receipt verifier cannot pass.

The CI workflow `global-parity.yml` runs the offline checker and a separate explicitly allowlisted cross-domain test suite, reusing the shared Realtime evidence parser and revision binding. Run locally only with admitted compilation on shared hosts:

```sh
python3 -B scripts/global_parity_evidence.py --host-admission --output /tmp/global-parity-receipt.json
```

## Real Rust differential acceptance (#90)

The manual `rust-differential.yml` workflow builds the C# test assembly, downloads the official Linux x64 Rust v0.172.0 package with a fixed SHA-256 (the release tag resolves to the pinned commit), and runs five independent filesystem scenarios against both the public native handler and the actual Rust App Server via stdio. It creates a fresh credential-free home, requires a separate Linux network namespace with loopback only, and uses temporary fixture paths. It does not launch provider calls or user commands. The five scenarios compare binary round trips, directory/metadata projection, invalid base64 and relative path errors, and recursive copy/remove effects. Timestamps are checked for type, not equality between separately created files.

The differential receipt is a distinct `rust-runtime-differential` lane, with upstream package and executable digests, exact managed source tree, per-case outcomes and isolation evidence. A failed/skipped case cannot make it eligible. Neither a successful bridge nor an offline mock is native SDK acceptance; independently review the actual behavior and map each exact scenario before any row can receive credit. Ordinary CI and release workflows do not execute the Rust process or promote these receipts automatically. The first completed run at `eb8bf2e` passed all five cases (zero skipped or failed); its digest-verified receipt is `docs/global-parity-evidence/rust-fs-eb8bf2e-45958822314.json`. Seven RPC rows reference the applicable real-runtime observations via `runtimeEvidence`. The verifier rejects mismatched case sets, receipts, platforms, pins, executable identities, missing isolation or incomplete runs. These observations do not grant complete RPC or native acceptance. The initial run was aborted before tests because VSTest requires loopback; the retry enabled only isolated loopback and dropped elevated privileges.

The manual workflow also supports independent `thread-lifecycle` and `model-catalog` scopes. The former compares empty named-thread resume across host restart and archive/read/unarchive on actual Rust, using a synthetic static model catalog and a managed in-memory CAS store. It does not certify multi-client notification fan-out, real database durability, or a subsequent provider turn. The latter compares the same synthetic catalog's display order, default, hidden models and pagination. Each scope produces a separate receipt; a failing or incomplete scope cannot certify another scope. No provider calls are allowed in these fixtures. At `6143759` the corrected fixture supplied the required Rust model instructions; both scopes completed successfully (2/2 thread lifecycle and 1/1 static model catalog, zero failures/skips), with all seven workflows green. The first attempts failed because the fixture lacked a mandatory catalog field, not because runtime behavior was proved divergent. Seven existing typed contract reviews remain intact, with separate revision-bound runtime observations where applicable. In total, 16 RPCs now reference verified runtime observations. The static model test does not establish provider-backed catalog display order; Rust's provider-backed ordering test and the native priority sort still need an explicit differential scenario. The thread tests do not certify native `historyMode` parameter acceptance or a completed subsequent turn.

## Release gate (#53 + #91)

The global gate is deliberately red until independently reviewed scope, exact-revision offline evidence, applicable platform and host evidence, optional Rust interop, actual live provider acceptance and the Realtime gate all pass. Reuse `scripts/realtime_parity_evidence.py` for revision-bound offline receipts; extend evidence support to explicit credential-free non-realtime classes instead of running authenticated tests implicitly. Never publish on catalog parity or build success alone. The publish workflow consumes the combined global report, which incorporates the existing Realtime gate and requires both lanes to be ready. This only tightens the existing publication condition; ordinary CI remains enabled and the owner-controlled publication switch is unchanged. Coordination with Agent 5 remains required before any release.
